# 知识库 / RAG 第三阶段：排期、决策与开放问题

## 这份文档是什么

第二阶段（产品完整度）之后、第三阶段（优化提优）的**待办队列**——装还没落地的排期、已定但未执行的决策、以及待验证的假设。

**归属规则（重要）**：

- 这里只放**尚未落地**的东西。某项做完了，就把结论迁进 `notes/`（知识沉淀）或 `docs/context.md`（项目状态），**并从本文档删掉**——不留副本。
- 一旦开始留副本，两处必然漂移，半年后没人知道该信哪份。
- 所以本文档只会变短，不会越写越长。

## 二、已定的决策

### 2.1 PDF 解析不单独立项，并入切块优化

单做 PDF 解析 = 调包（`pypdf` 五行代码），没有工程含量。真正有深度的是**版面分析**（识别标题 / 正文 / 表格 / 页眉页脚，按区域抽取重排）——RAGFlow 的 DeepDoc 自研了模型，MinerU / Docling / Unstructured 是第三方方案。

**关键认知**：PDF 解析的价值不在解析本身，在**它和切块的耦合**——版面分析告诉你「这行是二级标题」，heading 感知切块器才有东西可用。

所以形态定为：**PDF 结构化解析 → heading 感知切块 → 双份数字**（解析质量 + 检索质量）。解析器本身（MinerU / Docling / 多模态 LLM）是可替换的选型题，我们的活儿在「结构信息怎么保留并喂给切块器」。

> 待办：调研四家（RAGFlow / Dify / llama_index / MaxKB）文档解析源码，看清哪些自研哪些调包、解析产物形态、如何与切块耦合。prompt 已发出，结果回来后归档到这里或 notes。

### 2.2 语料问题已解（不需要"生产环境的 PDF"）

需要的不是「生产环境的 PDF」，是**「有代表性难度的 PDF」**。公开语料反而更好：可复现、无保密问题、别人能验证数字。

三条路：

1. **[OmniDocBench](https://github.com/opendatalab/OmniDocBench)**（CVPR 2025，OpenDataLab，2026-04 更新至 v1.7）——981 页 PDF，9 类文档（学术论文 / 财报 / 报纸 / 教材 / 手写笔记），中英双语，**带表格 HTML+LaTeX 标注、公式标注、15 类版面元素定位**。现成的标注，直接对分。
2. **免费真实中文 PDF**：arXiv 论文（双栏 + 公式 + 表格）、巨潮资讯网上市公司年报（海量中文表格，最贴近企业知识库）。
3. **测试集不用手工标**：LLM 给每段生成「它能回答的问题」→ 天然得到 qrels（`rag-retrieval/qa.md` Q11 早记过此法），与现有 recall/MRR 尺子无缝对接。

### 2.3 生成端评测自己写，不装 RAGAS

指标本身很有意义（RAG 的命门就是「答案有依据」，而现在没有任何数字能证明这件事）；但 RAGAS 那个库内部就是几个 prompt，中文 prompt 一般、版本变动大。

**faithfulness 的算法**：把回答拆成原子陈述 → 逐条问裁判模型「这句能否由检索到的上下文推出」→ 支持数 / 总数。配套还有 answer relevancy、context precision。

自己写的理由：① `benchmarks/` 骨架已在，加个脚本的事；② 面试必然追问「怎么算的」，自己写过才答得上。口径对齐 RAGAS 即可（文档里写明「指标定义对齐 RAGAS」）。

### 2.4 不换 dense embedding 模型

现有所有实验结论——w=0.9 最优、hybrid 域依赖、rerank 双域分化、HNSW 20 倍——**全都长在 `bge-large-zh-v1.5` 上**。换 dense 模型的代价：两域各 1 万段重灌 + 重建 HNSW + **所有历史档案数字瞬间不可比**。

收益侧则未经测量：电商域 recall@10 已达 0.929（老模型跑的），天花板不低，边际空间有限。而「用了更新的模型」在简历上是一行字，没有工程含量。

**结论**：ROI 最低的动作，不做。真想比，第三阶段有空时当**一次带对照的实验**（两模型各灌一版、同批 query 跑分），而不是直接换掉地基。

### 2.5 异模型双腿：dense 和 sparse 不必来自同一个模型

**这条推翻了一个常见的默认假设**。业界叙事把 BGE-M3 的卖点说成「一个模型同时出 dense + sparse」，容易让人以为两路必须同源，于是把选型逼成「自托管 BGE-M3 拿 sparse」vs「调 API 用 Qwen3 拿更强 dense」的二选一。

但 **RRF 只吃名次，不问名次是谁给的**（`fuse_rrf` 是纯函数，输入两个排序列表）。ES 选型那条早就写过同一道理：「融合本就在应用层，两腿异引擎天然支持」——**两腿也天然支持异模型**。

所以第三条路：**dense 腿一个字节不动（继续调 API），只用本地 BGE-M3 算 sparse 那一路**。好处是既有基准全保住、实验变量单一、不碰产品架构。

## 三、已查证的技术事实

### 3.1 BGE-M3 sparse 不做「词项扩展」

常见误解：「搜『施工帽』，BGE-M3 会把『安全帽』也扩展进 query 向量」——**没有这回事**。那是 **SPLADE** 的行为（用 MLM 头在整个词表上算概率，能给原文没出现的词赋权）。

BGE-M3 的 `lexical_weights` 只对**输入里实际出现的 token** 算权重。[Zilliz 对比文章](https://zilliz.com/learn/bge-m3-and-splade-two-machine-learning-models-for-generating-sparse-embeddings)：BGE-M3 只在 query 和文档**有共同 token** 时才产生非零相似度，跟 BM25 一样。[跨语言检索论文](https://aclanthology.org/2025.mrl-main.16.pdf)实测 SPLADE++ 赢 BGE-M3-sparse，原因正是前者有词项扩展。

**准确表述**：BGE-M3 sparse = 学出来的 **term weighting**（这个词有多重要），不是 **term expansion**（补同义词）。它治「词权」，**不治词汇鸿沟**——那活儿仍归 dense。

### 3.2 硅基流动 API 拿不到 sparse（实测）

对 `BAAI/bge-m3` 调 `/v1/embeddings`：

```
顶层字段: ['object', 'data', 'model', 'usage']
data[0] 字段: ['embedding', 'index', 'object']   ← 只有 dense，1024 维
```

试过五种可能的开关：`return_sparse` / `return_dense`+`return_sparse` / `sparse` / `extra_body` 包一层 → **均 200 但被静默忽略**，字段一个不多；`encoding_format: "sparse"` → **400 参数非法**。

根因：它走 **OpenAI 兼容协议**，而该协议的响应结构里**根本没有放 sparse 的位置**。`lexical_weights` 是 FlagEmbedding `M3Embedder.encode(..., return_sparse=True)` 的独有能力，托管商要暴露它得自定义非标接口——硅基流动没做。

**推论**：要 BGE-M3 sparse，**必须自托管**（FlagEmbedding，模型约 2.2GB，Mac 可用 MPS 跑）。这把「换个模型名」变成了「引入本地推理服务」，与现在「只管凭证和 HTTP」的架构前提冲突——故降级为离线实验（见 §4.1）。

### 3.3 PG 的 `ts_rank` 没有 IDF 是架构性的

不是「公式里缺了一项」，而是 **`ts_rank(tsvector, tsquery)` 是逐行函数，只看得见当前行的 tsvector，拿不到全库统计**。PostgreSQL 官方文档明说排序函数「不使用任何全局信息」。

**这个区别很要紧**：若只是公式缺项，换个打分函数就能救；既然是「打分时看不到全库」，那在 PG 里**怎么改打分函数都救不了**——得改索引结构（存 docFreq），等于重新实现半个 Lucene。这才是 `rag-retrieval` §24 那句「sparse 的天花板」为什么是天花板。

IDF 的时机：**统计在建索引时备好（document frequency），乘法项在查询打分时生效**，表现形式就是排序——稀有词命中的文档排前面。我们实测的活体标本：keyword 路三条并列 `0.231`（手机靓号 / 老人报警器 / iPhone13 手机壳同分），因为「手机」和「手机壳」在 `ts_rank` 眼里一样重。

### 3.4 Qwen3-Embedding 是纯 dense

全系列（0.6B / 4B / 8B）建立在 Qwen3 dense 基座上，只出 dense 向量，**不出 sparse**。卖点是 dense 效果强 + MRL 可裁剪维度 + 指令感知。选它就意味着 sparse 那一路要另想办法（ES / PG 扩展 / 传统分词器 / 干脆不做）。

### 3.5 SPLADE：可以否决

Naver Labs Europe 出品，**只出 sparse 不出 dense**，独门是词项扩展。对中文 RAG 否决，三个理由：中文支持弱（主流 checkpoint 英文为主）、要单独再跑一套模型出 dense、BGE-M3 的 sparse 已够用。留个印象即可，不投入。

## 四、待验证的假设

> 这一节和 §2 §3 严格分开——**「已定决策」和「待验证假设」混在一起是最容易骗自己的**，半年后容易把当初的猜测当成结论。

### 4.1 BGE-M3 sparse 能不能填上实验矩阵缺的那一格

**背景**：现有的双域实验只覆盖了 2×2 里的两格——

| | keyword 腿弱 | keyword 腿强 |
|---|---|---|
| **两路正交**（语义 vs 词面互补） | ✅ 医疗域（0.205，hybrid +0.5pt） | ❓ **空着** |
| **两路冗余**（词汇表重合） | — | ✅ 电商域（0.557，hybrid ≈ 0） |

由此得出的结论「**互补性 > 腿强度**」，是拿「弱但正交」和「强但冗余」对比出来的——逻辑成立，但**右上角那格从没测过**。

**假设**：BGE-M3 sparse 在医疗域，正好落在那一格（既强、又与 dense 正交）。

**实验价值不是「换个更好的分词」，而是验证自己那条结论的边界**。两种结果都值钱：

- 增益仍很小 → 结论从两点连线升级成三点确证，「互补性主导」站得极稳；
- 增益明显变大 → 亲手推翻自己此前的结论。

**判断依据**：别为了「上新技术」而上 BGE-M3，要为了「填那一格」而上。前者是跟风，后者是实验设计。

**执行形态**（成本可控）：
- 产品架构**一行不动**，keyword 腿继续 PG FTS，认它的天花板；
- 在 `benchmarks/` 做一次性离线实验：本地跑 FlagEmbedding 算 sparse → 存 pgvector 的 `sparsevec`（0.7+ 已支持，我们是 0.8.1）→ 与**现有 dense 腿**（不换模型，见 §2.5）做 RRF → 双域对照；
- 出完数字归档，产品照旧。

**与 rerank 双域结论的关系**：rerank 验收已给出「二次打分的收益取决于域、不取决于模型」（医疗 +2.5pt/+2.2pt，电商 −2.8pt/−2.4pt）。加上 hybrid 的双域结论，**域依赖这条线已有四个数据点**。BGE-M3 sparse 实验是第五个，且是唯一能检验「腿强度」这个自变量的。

## 五、永久挂账（附否决理由）

| 事项 | 否决 / 挂账理由 |
|---|---|
| **ES（本地单容器重考 sparse）** | pg_search 三票否决（1Panel PG 装插件 = 容器手术、生态小众、面试认知度低）；ES 本身是「基准实验 ≠ 生产部署」的载体，但优先级低于第三阶段全部事项。**若 §4.1 的 learned sparse 路线走通，本条基本可以永久关闭**——表示层变强后引擎生态就不重要了 |
| **自定义词库（ik / jieba 用户词典）** | 只在 sparse 腿上有意义，而 sparse 的两条升级路（上 ES / 换学习式表示）都不需要它。且已预判：无 IDF 打分器会压制「长术语成词」的收益，单独考仅 +低个位数 pt |
| **Milvus 可插拔** | 能做，但**接入点和现有 `Retriever` ABC 不是一个维度**——现有抽象管的是「用什么算法检索」，换存储引擎管的是「数据存哪、谁来算」，是正交的两轴。要支持需在 vector 腿**内部再抽一层 `VectorStore` ABC**（upsert / search / 建索引），因为 `vector.py` 目前直接写 SQL。**现成参考**：MaxKB 的 `apps/knowledge/vector/`（`base_vector.py` 抽象 + `pg_vector.py` 唯一实现），正是这个形状 |

## 六、不在本项目做的（简要）

以下能力 MaxKB 已具备且更成熟，本项目不重复建设：多格式文档解析的体力活部分、外部数据源同步（web 站点 / 飞书 / 语雀）、知识库工作流与版本、术语库、标签体系、段落级运营（排序 / 迁移 / 命中计数）、导入导出。

另注：MaxKB 的「命中处理方式」（相似度 ≥ 阈值直接返回原文、不过 LLM）与本项目**架构不适配**——它的检索是工作流节点，跳过后续 LLM 节点很自然；而本项目是 Agentic RAG，LLM 先决定调 KB tool、检索才发生，「不过 LLM」在时序上讲不通。**不移植**。

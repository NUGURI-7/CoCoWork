# CoCoWork Context

## 项目概述
- CoCoWork 是一个个人独立开发的 full-stack 项目，后端使用 FastAPI，前端使用 React 19。
- 当前定位：AI Agent 管理平台（暂定方向，随开发推进持续演化），核心能力包括多 Agent 编排与调度、RAG 混合检索、Prompt 版本管理、Skill 技能市场、知识库管理。
- 这个文件是后续 AI 新对话的单一项目上下文来源。

## 早期方向参考（低权重）
- 这部分只用于提供产品方向上的大致印象，帮助 AI 理解项目可能的长期演化方向。
- 这不是正式需求，不构成强约束，也不代表相关能力已经实现。
- 如果与当前代码现状、你在当次对话中的明确要求或后续决策冲突，应以实际项目状态和当前任务为准。
- 远期愿景：可管理、可编排、可扩展的一站式 Agent 平台，支持语音交互（ASR/TTS）与视觉理解多模态输入输出，提供多层 RBAC 权限管控与资源隔离。
- 当前阶段聚焦基础设施搭建和核心后端能力验证，前端仅做满足测试和验证需要的最小实现。

## 产品 / IA 决策（2026-05-22 敲定，中等权重）
- 定位：团队管理 + 个人使用；普通用户进个人工作台，admin 另有独立后台。
- 主界面：左侧 sidebar 工作台（非 chat-first）。大模块：Agent / Knowledge / Tool(待定) / Model；Prompt 并入 Agent 配置、不单列。落地页 = 个人主页(dashboard)，从主页或 sidebar 进各模块。
- 不引画布编排：声明引用 + 后端持有拓扑（LangGraph 模板 single/supervisor/pipeline，表单填槽）；多 agent = supervisor / agent-as-tool；只读拓扑图后置。
- Agent 可配置/可发布，发布后对外暴露对话，目标「统一会话内多 agent」。agent 卡片：点卡片→配置编排，点按钮→对话。
- 对话：配置页 Playground(调试) + 发布后 chat 路由(正式)。
- Knowledge 可被 agent 关联为 RAG 外挂；每库配 embedding；文档编辑用自封装 tiptap(后做)。
- skill/tool 放外置沙箱跑；用户能否上传待定；skill 暂缓。
- admin 入口藏头像下拉(仅 admin)；admin 是独立 `/admin` 分区（与工作台平级、不嵌套）。
- MVP 聚焦：先简单 agent 跑动 + RAG 混合检索；功能铺完再做 agent 能力/检索准确度/调度执行优化。

### 2026-08-01 — 跨回复历史压缩整片收官（切片 3-5）

**做完的事**：对话超线时停下来把旧历史压成一段中性摘要存表，只留最近一截原文。设计稿里叫「Compress 层 B」。它跟**一次回复内部**那个压缩器（框架送的 `SummarizationMiddleware`）是两件事——后者压的是单次 run 内工具往返的堆积、run 结束即弃；跨回复这半 deepagents 帮不上，**因为我们的历史每轮从 DB 现拉现渲染**（视角化的固有代价，用不了 checkpointer），住在运行状态里的压缩器够不着。

**阈值全部从窗口派生，换模型只改一个数**：窗口 200K（锁 DeepSeek）→ 触发 170K（85%）→ 保留 20K（10%），比例照抄 deepagents 默认值。**170,000 恰好等于它「读不到模型窗口时」的兜底默认**——独立算出来撞上，说明这条线站得住。判据用 `conversation.context_tokens`（模型上报的真实值），估算只用在切点上：赌注小，估偏了只影响留多少、不会该压的不压。**顺手修了个坏保险丝**：一次回复内那个压缩器原来写死 `trigger=200_000`，正好等于窗口本身——消息要堆到 20 万才触发，可堆到 19 万那次调用加上系统提示和工具定义早就超窗报错，压缩永远轮不到跑。改成共用同一个常量。

**四个落点**：`agents/workspace/history_budget.py`（新，数 token + 找切点）/ `services/workspace/compaction_service.py`（新，取原料 → 调管家模型 → 写表）/ `view_context_assembler.py`（`NEUTRAL_VIEW` 中性视角 + `split_at_cursor` 按游标切两半 + `build()` 收摘要）/ `stream.py`（装配从流外挪进流内，流外只留轻量预检保住 400 语义）。

**数 token 不引分词器**：字符估算 2.5 字符/token。Dify 拿 GPT-2、Letta 拿 tiktoken 数所有模型，都是明知不准照用——**「接受近似」才是业界形态**，动态自校准没人做。切点三规则：往回累加、顶过预算的不要（留下的只会少于预算）；切口落在 user 消息前保证一问一答完整；**至少留一轮**。

**摘要形态**：五节骨架抄 langchain 默认提示词（用户目标与约束 / 重要结论 / **各成员的产出** / 产出说明 / 待办），两处必须改造——① 人称：它给单 agent 写的通篇「你」，我们必须中性第三人称具名（一份摘要全员共用，「我」指谁会当场错乱）；② 加「各成员的产出」那节（单 agent 没有派活这回事，糊进 SUMMARY 里署名就掉，直接复发「成员产出被冒充」）。自加铁律：**只写结论不写动作**——摘要天生是文字、没法给它结构化字段兜底，唯一防线是别留下可模仿的动作样本。

**产物清单归平台不归模型**：摘要只写「这东西是干什么的」（语义，模型擅长），文件名和大小由平台从表里拼成一条清单跟在摘要后（事实，模型会猜——实测它写过 `chart.svg (3KB)` 而真值 3598B）。**与 deepagents 的关键差别**：它的 agent 有 `ls` / `read_file`，清单错了一 ls 就纠正；我们每轮工作区全空、只有 `fetch_artifact(filename)`，**清单就是唯一的地图**，画歪了就取不回来。被压掉那批的产物不合并就跟着原文一起消失——零额外成本，拼上下文时本来就把全对话产物查出来了。

**失败三层**：① 摘要生成失败**绝不落表**（表 append-only、跨轮复用、下次压缩还拿它当原料，写进一条坏的就是永久失忆）—— langchain 那个 `return f"Error generating summary: {e}"` 把报错字符串当摘要用，它压完一轮就扔勉强说得过去，**我们不能抄**；② 这一轮降级用全量历史照常跑完；③ 全量真塞不下才机械截断。**空摘要单独判、不混进 except**：模型正常返回空串不是异常不会抛，不判就会写一行空摘要进表，**比报错更糟因为它看起来是成功的**。

**实测（窗口临时调到 8000 跑真对话）**：`10,542 → 5,022`，**砍掉 52%**。摘要 291 token / 726 字，五节齐全、零第一人称、零动作转述、记住了「SVG 方案被否决及原因」。压缩后模型接着写「六、国际比较」编号接得上——那信息只在摘要里。**「至少留一轮」在生产里救了场**：日志 `封存=10 条 保留=2 条`，保留的那条 supervisor 回复自身 2,565 token 远超当时 800 的预算，是兜底规则把最后一个来回捞了回来。

**测量口径两个坑**：① `source_tokens` 是**触发时的上下文水位**、含固定开销（本次实测 ≈2,800，**按空间变**——设计稿里那个 5,534 是另一个挂更多工具的空间），拿它除 `summary_tokens` 算压缩比是虚高的，效果看逐轮曲线（迁移 0025 已把这句写进列注释）；② 派活那轮的 `prompt_tokens` 会是尖峰（实测 44,953），那是「同一段历史重发几次算几次」的账单口径、不是上下文，看膨胀要盯没派活的那几轮。**cache 命中率那半砍掉**：我们明确决定过不单列缓存字段，而且**视角化换人**是压缩治不了的更大杀手（换应答者历史整个重渲染、前缀从第一个字就变），量出来会被它淹没。

**前端**：`compact_start` / `compact_stop` 两个事件；压缩期间列表底部「正在整理对话记录…」（这两帧在 `message_start` **之前**到，此刻还没有 assistant 气泡，提示只能挂列表底）；压完在本轮消息上方留一条「已整理此前的对话记录」分隔线，**刷新后消失**（产品决策）。线的位置是近似的——真实边界更靠前一个来回（保留段仍是原文），差一轮不影响「从这儿往上模型记得就模糊了」这句话成立，**已知不改**。`ok:false` 不弹错不画线：那是降级、不是错误。

**已知未做**：压缩自己烧的 token 没记账；supervisor 会对用户漏出 `member_019fbc36` 这种内部键（既有问题，不是压缩引入的）。

### 2026-07-31 — 会话标题自动生成（Workspace 最后一个排后小件收官）+ 时区收口

**形态推翻了 backlog 的写法**。原计划「BackgroundTasks 异步起名 + 进对话 lazy 兜底」，实际做成**一个独立端点，由前端在点发送的同时与对话流并发发出** —— `POST .../conversations/{cid}/generate-title`，body 带那句话的纯文本，返回 `{title}`。**`stream.py` 一行未动**。

**三层否决，逐层记账**：① **不用 `BackgroundTasks`** —— 它绑在 response 上，SSE 场景下要等整条流跑完才触发（workspace 多 agent + 工具常跑几十秒），标题就晚几十秒出现，异步的意义全丢；② **不进 SAQ** —— 判据是「这活丢了要不要有人负责」：文档向量化丢了用户永远卡 processing（必须有人负责，进队列），起名丢了下次进对话自动补上、用户根本不知道（没人负责，不进）。**Dify 是活证**：它有完整 Celery（30+ 任务、多队列，连「删对话」都走 `@shared_task(queue="conversation")`），唯独起名用裸 `threading.Timer` 守护线程——有队列 ≠ 什么都进队列；③ **不用后端 `asyncio.create_task`** —— 并发性上它和前端发第二个请求完全等价，差别只在「名字生成好了谁告诉前端」。端点有返回值，前端 `set` 一下就完；后端分流则要新增「流结束」钩子（只能挂进 `chat-registry` 那个刻意与组件生命周期解耦的公共机制）+ `loadConversations(force)` 整表重拉（对话列表是按 workspace 缓存的一次性加载，不随每条消息刷新）。**Open WebUI 同款**：`POST /api/v1/tasks/title/completions` 由前端 `generateTitle` 调，它把「后端自己起名」另做成一种模式给不走它前端的 API 用户。

**触发点不在通用对话层**：发送实际发生在 `MessageInput → chat-store.send()`，那层是 Playground / workspace 共用的、刻意不认场景。改在 `WorkspaceChat` 里用 selector 读「第一条 user 消息的文本」+ 一个 effect —— **通用层一行不动**，而且白捡 lazy 兜底：进对话 hydrate 完历史同样会触发（条件都是「本地 title 为空」）。

**占位与真标题必须分开存**：`conversations[].title` 永远只等于库里那份（「为空 = 还没起过名」是触发起名的唯一判据），前端占位（用户那句话前 10 字）单独一个 `titlePlaceholders` map、渲染时才叠上去（`真标题 → 占位 → 新对话` 三级回落，收口成 `useConversationTitle`）。并发闸另用模块级 `Set` 而非兼任占位 —— 起名失败时占位要留着（比跳回「新对话」好看），但又必须允许下次重试，两个诉求打架。

**失败不降级（不写截断标题进库），留空等下次重试** —— 这条被回填实测反向验证：第一轮 6 条失败，原样重跑 4 条直接成功（上游偶发抖动）。当初若照 Dify 写截断版兜底，这 4 条就永久锁死成一个平庸标题（条件写 `WHERE title=''` 会挡住后续覆盖）。

**踩坑一：推理模型把 `max_tokens` 吃光**。`max_tokens` 是「思考 + 正文」的总预算，`deepseek-v4-flash` 实测 128 全被 reasoning 吃掉、`finish_reason=length`、`.text` 为空 → 起名随机失败（另一条 `reasoning:111/总122`，只剩 11 token 给正文，险过）。**这不是回填独有，线上任何人把管家配成推理模型都中招**，改 `_TITLE_MAX_TOKENS=1024`（这个闸是防跑飞不是省钱；非推理模型有 prompt 里「不超过 20 字」兜着，给多少都只吐二三十个 token）。**顺带纠正一个误判**：不继承 `reasoning_effort` 并不能关掉思考。实测 `reasoning_effort="none"` / `extra_body={"thinking":{"type":"disabled"}}` 都能关、延迟 1.1~1.4s → 0.7~0.8s、标题质量无差，**但决定不接** —— `param_adapter` 的 key 是 **LC provider 家族**（`openai` 一格罩着 DeepSeek/通义/SiliconFlow/custom 全部），加进去等于对所有兼容端点盲传；且那层作用于所有调用、全局关思考是错的。剩下只有「传 + 400 回退重试」，为 0.5 秒加一条永久路径不值。**真正的落点是 `AIModel.meta` 的模型能力标记**（现在还是 `None`），有了它才能按模型一格一格开。

**踩坑二：两个同名 `TextBlock`**。`runtime.blocks.TextBlock`（运行时块层，`parse_blocks` 产出）vs `schemas.agent.chat_schema.TextBlock`（协议层，`runner.content_to_text` 的 `isinstance` 比的是它）。接错**不报错、静默返回空串**。产品代码三处调用都配套，回填脚本一接就中招。

**存量回填**：26 条旧对话补齐 25 条（余 1 条零消息空对话，本就该跳过）。`QuerySet.update()` 不触发 `auto_now`，回填没有打乱列表排序。

**顺带修掉时区（老 bug，全库时间字段受影响）**：`use_tz=False` 时 `auto_now` 写的是**写入进程当时的墙上时钟且不带时区标记** —— 现在恰好对，只因 dev server 进程 TZ 是 UTC；哪天从 `TZ=Asia/Shanghai` 的终端起服务，写进库的就是错时刻（数据错，且事后无法分辨）。序列化又不带 `Z`，浏览器 `new Date()` 按本地时间解析 → 时间戳跑到未来 → `timeAgo` 的 `diff` 为负 → `Math.max(m, 1)` 兜成「1 分钟前」，**几小时内的对话全塌成同一个显示值**（正是它把这个 bug 藏了这么久）。改 `use_tz: True` + `timezone: "UTC"`：列本来就是 `timestamptz`、存量存的也是正确 UTC 时刻，**无需迁移**；`app/` 里唯一自造 datetime 的 `security.py:28` 本就用 aware UTC，零影响。`timeAgo` 手写拷贝共**四**份（`Home.tsx` / `AgentCard.tsx` / `ConversationList.tsx` / `WorkspaceCard.tsx`），**2026-07-31 已收敛**——不是抽公共函数，而是统一到项目早就配好却没用的 dayjs `fromNow()`（`main.tsx` 的 `relativeTime` + `zh-cn` 一直在，`DocumentList` 也一直在用），手写版连同那行 `Math.max(m, 1)` 一起删除。

### 2026-07-31 — 跨轮回放协议改造：喂给模型的历史里放回「事实」

**病根一句话**：`ViewContextAssembler` 每次回复前重拼历史时，把过去的工具调用**压平成一行自然语言痕迹**（`〔我 调用了工具 X → 完成〕`），`result_data` 一个字不回放。于是两个症状：① 答不出上一次回复里工具查到的内容；② supervisor **空手编造派活**（实测：用户发消息 10 秒后回复、`tool_use` 0 条、产物表无行，它声称的 message_id 库里根本不存在）。根因是**压平的那一刻，「真调用过」这个事实就从平台写的结构化字段掉进了模型自己能写的文本通道**——prompt 禁令拦不住（7-29 `a845206` 加过，照编）。

**为什么只有我们有这个问题**：单 agent 产品历史是一条固定消息列表、存什么喂什么，没有「渲染」这一步；我们因为**视角化**（同一段历史管家看是「我派了活」、成员看是「Supervisor 派活给你」）必须每次重拼，重拼就丢结构。这是多 agent + 视角化自带的代价。

**改法三档**（`docs/design/history-replay-v1.md` §5.1 三件套 + 正交的结构化决策）：

| 这条历史消息 | 怎么渲染 |
|---|---|
| **viewer 自己发的** | 还原成原生 `AIMessage(tool_calls=…)` + 配对 `ToolMessage`（`_render_own`）。切分单位 = 一次模型交互：「文字→工具→文字」本就是多次交互攒的，遇工具后再见文字即开下一条 AIMessage |
| **别人发的** | 仍走 `<msg from="X">` 文本痕迹，但**把结果带上**（原来直接丢）。结构化塞不进去——那语义是「你调用了它」，而它根本没调、甚至没挂那个工具 |
| **带 subagent 戳的** | 照旧整体跳过（成员交付内容已在 task 块结果里） |

**必须自己付的代价**：API 硬性要求每个 `tool_call` 配一条结果，而库里 **12% 的块没有结局**（用户中途点停止）——补一条 `ToolMessage(status="error", content="（调用被中断，没有结果）")`。这是压平方案当初白捡的便宜。单测里 `assert_paired` 就是这条不变式的哨兵。

**大结果封顶（offload 三件套）**：超 `MAX_TOOL_OUTPUT_CHARS`(=4000，从 `CoCoTool` 提成模块常量、两处共用同一个数) 的结果只留**前 500 字 + `tool_use_id`**，配新工具 `read_tool_result`（`app/tools/tool_result_fetch.py`，per-run 绑 conversation，`content @> '[{"id":…}]'` 在 jsonb 里直接定位）。**只在历史里真有截断时才挂**——`build` 改返回 `AssembledContext(messages, truncated)`，标记与工具同源，避免「有标记没工具 = 指死路 / 有工具没标记 = 白占位子」。保留 500 而非留满上限：留满等于没封顶，这 500 字是**标识**不是更小的上限。

**实测定的阈值**（脚本量了库里 358 个 tool 块）：282 个带 subagent 戳（跳过）；应答者自己的 76 个里 p50=161、p75≈1200、最大 4,750；单个对话累计最大 15,786 字符 ≈ 8K token。**没保护的是三条路**：MCP（单次见过 26,049）、deepagents 文件工具（14,143）、成员交付内容。阈值 4000 只截住 76 里的 3 个。

**产物清单挪出模型自己的消息**（当天实测复现后追加的一改）：`<artifacts>chart.svg (3KB)</artifacts>` 原来拼在 supervisor 自己那条 `AIMessage` 正文末尾 → **模型照抄了**，自己写出一行（大小是猜的、错的），那串内部标记被前端当正文渲染给用户看了。改成**紧跟其后独立一条** `HumanMessage('<msg from="System"><artifacts>…</artifacts></msg>')`：模型的输出永远是 assistant 角色，变不成这条 user 角色的消息，样本从它眼前消失。base prompt 加第四条发言者约定。**否决的两个替代**：放 system prompt（每产出一个文件就整段 cache 失效）、改成 pull 让模型自己查（deepagents 同款，但它那是同一次 run 的活文件系统，我们的产物跨回复躺在对象存储里，每次要用都得先查一遍反而啰嗦）。

**验证**：18 条单测（`tests/test_view_context.py`，配对不变式 / 视角分叉 / 截断 / 跳过规则）+ 拿真实对话跑 assembler dump 出消息列表逐条核对 + `read_tool_result` 在真库上闭环（截断标记里的 id → 取回 4,219 字符全文）+ 用户真机复刻 7-30 那次翻车场景，不再编造。

**顺带**：assembler 里那批私有 `@staticmethod` 全改回实例方法——它们是纯函数不假，但类里写 `ViewContextAssembler._cap_result(...)` 读起来像在调另一个类，而「不需要实例就能调」这个好处一次都没用上。

### 2026-07-30 — P5「Skill 执行 + 沙箱」整片收官（跨对话拖引用 + 61 条单测）

**P5 全貌**（决策与依据全在 `docs/design/skill-sandbox-v1.md`，含四轮修订记录）：agent 挂 skill → 一次完整回复借还一个**一次性容器** → 脚本在容器里跑 → **交付区**（`/outputs/<message_id>`，每轮新建的空目录）里的文件收进对象存储成为产物。三个进程形态：web / worker / **sandboxd**（独占 docker SDK，web 进程永不碰）。内置 skill 不入表（本体在 `app/skills/builtin/`，表里只可能有「用户给它配的 key」那种行）。

**本次两件**：① **跨对话拖引用（决策 25）** —— 用户把右栏产出物面板的卡片拖进输入框，后端据 id 查库 → 从对象存储取字节 → 灌进本轮 `/workspace`，**字节不经过浏览器**（引用的是已经在存储里的产物，不涉及 multipart，PDF/图片/xlsx 原样保真是白捡的）；② 沙箱纯逻辑单测 61 条。

**「引用 vs 实体」是这一片的切分线**（决策 14a 整条改判的根）：`/workspace` 每轮全空、什么都不自动铺。清单（一行文本、几十 token）全给，实体（一次对象存储往返 + 几十 KB~MB）一个都不给 —— 模型看着历史里的 `<artifacts>`（agent 产出的）/ `<attachments>`（用户附上的）标注，要哪个就调 `fetch_artifact` 取哪个。每轮固定开销 = 一次 DB 查询，**与这个 workspace 攒了 3 个还是 300 个产物无关**。原方案按「本对话 / 跨对话」切，于是「铺几条」「什么算本对话」「同名铺哪个」全要现编答案且都站不住 —— 换线之后一起消失。

**拖引用的两阶段**（新模块 `services/sandbox/attachment.py`）：`resolve_refs` 只查库、校归属、回填展示字段，跑在**落 user 消息之前**（引用无效 = 请求错误，与上方「@ 到无效成员 404 不落库」同一条规矩）；`inject_attachments` 读字节、灌工作区、拼 `<attachments>` 标注，跑在**沙箱装配之后**（工作区路径由 driver 决定，装配前不存在）。合成一趟就得把落库推到装配之后 —— 装配一报错，用户刚说的那句话就蒸发。

**三个口径**：① 请求里**只有 `artifact_id` 作数**，`filename/size/content_type` 一律以库为准回填 —— 落库那份因此自解释，前端回放与下一轮历史都不必再查库；② `fetch_artifact` 取值范围扩成「本对话产出的 ∪ 本对话拖进来引用过的」（那些属于**别的**对话，不扩就是「看得见 `<attachments>` 却取不回来」）；③ Playground 不接这套（决策 26，`prepare_stream` 一句守卫）。**没人挂 skill 时拖了文件不报错**（用户拍板）：消息照发、标注如实说「本轮没有能打开文件的参与者」——「附件只能给沙箱用」是现状不是永久前提。

**前端用原生 HTML5 拖放、不引 dnd 库**：一次性投递用不上 dnd-kit 的排序/动画/键盘可达性；代价是**触屏不工作**（桌面场景暂认）。**TipTap 的 drop 必须单独接** —— `prosemirror-view` 自己监听 drop（源码 `index.js:3803`），不在 `editorProps.handleDrop` 里 `return true`，拖来的东西会被它当文档内容插进去；它只 `preventDefault` 不 `stopPropagation`，所以外层容器的 `onDrop` 照样触发，两处都接 + 按 id 去重。桌面文件拖进来也要拦（不拦浏览器默认行为是**导航去打开那个文件**），目前只弹一句「暂不支持」。

**单测 61 条**（`tests/test_sandbox_*.py`，零 docker / 零 DB / 零网络，1.4s）+ **变异检验**：把「每轮清空 workspace」故意改坏 → 3 条立刻红，证明不是绿得没意义。共用假件 `tests/sandbox_fakes.py` **只实现被测代码真正调到的方法** —— 假件越像真的，越容易在真接口变了之后还静静跑绿灯。

**已知限制（记在设计稿 §5.5，别当 bug 查）**：同名文件的取回歧义（真解法是标注带短 id + 精确匹配，收尾期不做）、消息气泡里的产物卡片不可拖（产品判断：那儿不需要）、`resolve_refs` 的查库路径无单测（属集成层）。**P5 剩余**：用户上传 skill、本地文件拖入（用户明确后续要做，前端管道已铺好，缺上传那半段）。

### 2026-07-23 — 文档处理迁进 SAQ（P2 收官）+ `tasks/` 层定型

**状态职责三分**（迁移的真正内容，不只是换个调用方式）：service 标 `queued`（已入队）/ `process_document` 推进 `parsing→splitting→embedding`（真在跑）/ tasks 层标 `failed`（终态）。原来三处都在写同一批字段、互相重复。**`process_document` 改为异常外抛**——它过去自己 try/except 全捕、标 failed 后正常返回，SAQ 看到的永远是「任务成功」，重试无从谈起。

**重试语义 = 对前端透明**：失败先不声张，`ctx["job"].retryable` 为真就把 `stage` 退回 `queued` 等下一轮，三次用尽才标 `failed`。**中途绝不标 failed**，否则前端轮询会看到 processing→failed→processing 的抖动。新增 `DocStage.QUEUED`——`CharEnumField` 是 `CharField` 子类、落 PG 就是 `varchar(20)` 无 CHECK 约束，**加枚举值不需要迁移**（已查源码确认）。

**`app/tasks/registry.py` 契约表（本片主要设计产出）**：`TaskSpec` frozen dataclass 持 `name` + `timeout/retries/retry_delay/retry_backoff` + `enqueue()` 方法；`registry` 管契约、`*_task.py` 管实现、`worker.py` 管进程。三个决定：**①任务名带域前缀**（`knowledge.process_document`，agent 侧任务铺开后日志/指标能分清归属）；**②策略挂 spec 上、`enqueue()` 是 spec 的方法**——调用方不可能忘传 timeout（SAQ 默认 10 秒是这库最大的坑）；**③spec 不持 handler 函数**，持了就把 registry 拖进业务依赖。

**为什么不用装饰器**（Celery `@app.task` 式）：**①进程边界**——web 只需入队，装饰器天然让入队侧 import 实现模块，将来 MinerU 解析要拖几 GB 模型库、Skill 沙箱要拖 docker SDK，**这些绝不能进 web 进程**；**②多 worker 拆分**——重任务迟早要独占进程，`worker.py` 的显式 `functions` 清单直接按进程分组，全局装饰器注册是「全都注册进来」，反而挡路。代价（漏登记要跑起来才发现）落在 worker.py 那一行，是全项目最显眼的位置。**SAQ 自己不用装饰器同理**：它刻意不要全局 app 单例，且支持同一函数以不同名字登记。

**入队放 service 不放 route**：「标 queued」和「入队」必须成对，拆两层中间有窗口（状态已落库、enqueue 炸了 → doc 永远卡 processing）。单个失败回滚标 failed + 抛 503；批量逐个入队、个别失败不牵连其余、失败的标 failed 并归入 `skipped` 回前端。`document_service` 本就 import `storage`，再引 `queue` 单例同级不破层。

**读源码核准的三件事**：① `attempts` 在**执行前** +1，`retryable = retries > attempts`，故 `retries=3` 是**总次数**不是额外次数（默认 `retries=1` = 不重试）；② job kwargs 走 `json.dumps`，**UUID 传不过去**，入队侧转 str、任务函数里还原（脏东西只脏在边界一行）；③ 退避带 **jitter**——`base * 2^(attempts-1)` 算出上限后再乘 0~1 随机数，防批量任务失败后同时反扑（惊群）。

**实测两条路径**：正常路径 `queued`(0.16s)→`parsing`(0.64s)→`splitting`(2.2s)→`embedding`(3.2s)→`completed`(4.1s)，3 段 3 子块；重试路径（storage_key 指向不存在对象）三次尝试间隔 3.9s / 9.8s（5s 基数×指数×抖动），**status 全程 processing 一次没闪 failed**，终态 `failed` 且 stage 停在 `parsing` 一眼看出挂在哪步。

**前端**：`DocumentStage` 加 `'queued'`、展示态加「排队中」（warning 色系更淡的一档，与「向量化中」构成递进）。轮询判据是后端原始 `status==='processing'`，不受影响。**注意正常情况下 queued 只闪半秒**，要肉眼验就停掉 worker 再触发。

**刻意没做**：状态记账（判 retryable → 回落 / 标终态）**不抽基类**——它写的是 `Document` 自己的三个字段，agent 侧任务的状态机长什么样还不知道，N=1 猜不出该共享什么。真正的横切点是 SAQ 的 `before_process` / `after_process`（P7 埋点用得上），不是这个。

### 2026-07-22 — SAQ 异步任务队列基建落地（纯基建，业务零改动）

**选型三轮翻转后定档 SAQ**：ARQ（原技术栈写的）→ **官方已进维护模式，出局**；taskiq（多 broker / DI / 中间件 / 任务管道）→ **对 Redis-only + 任务独立的本项目过重，用不满**；**SAQ = Redis-only、开箱带监控 UI、复杂度配得上问题**。分工钉死：**Celery 靠 MaxKB 复盘兜「JD 硬通货」那档**（生产主流仍是 FastAPI 异步 web + Celery 同步 worker，两者不冲突），**SAQ 提供「异步原生范式 + 生态判断力」那档**——不指望小众库替 Celery 扛简历分量。技术依据：本项目后台任务清一色重 IO（等 embedding / LLM 网络返回），async 原生是真契合而非噱头。

**四件套（`app/tasks/` + `app/cli.py`）**：`queue.py` 队列单例（`Queue.from_url(..., name="cocowork")`，web 入队 / worker 取任务共用同一信箱，`name` 做 Redis key 前缀隔离，与 DaisyWind 及 app 其它 Redis 用途不撞）+ `worker.py` worker 配置（`settings` dict 被 `Worker(**settings)` 消费；**startup/shutdown 自己开关 Tortoise**——worker 是独立进程、不经 FastAPI lifespan；`functions=[]` 留作扩展点，加任务 = 往这登记）+ `cli.py` 两入口（`dev()` 起 web / `worker()` 起队列）+ `pyproject` 注册 `[project.scripts]`。**main.py 的 `__main__` 改为转调 `cli.dev()`**——IDE 按钮与 `uv run dev` 同一函数、杜绝配置漂移；lifespan `finally` 加 `queue.disconnect()`（队列自持一条 Redis 连接，与 RedisClient 各自独立）。

**读源码躲掉的两个坑**：① **SAQ 默认 `timeout=10` 秒**，向量化跑几分钟会被秒杀，入队时必须显式覆盖；② `ttl=600` 管的是**任务跑完后**结果留存，**不是**排队任务寿命——排队任务用普通 `set` 存、**不过期**，worker 停几天回来照样把积压全消化（持久性靠 Redis 自身持久化兜底，幂等任务可容忍丢失，故不折腾 AOF）。**实测捉到的真缺口**：worker 起来后**一声不吭**——`setup_logging()` 只在 main.py 顶层调，worker 这条路不经过它，日志全掉黑洞；`cli.worker()` 补一句 `setup_logging()` 后正常吐 `Worker starting: RedisQueue<...name='cocowork'>`。

**打包副作用（必须记）**：`[project.scripts]` 要生效得让 uv 把本项目当包装 → 加 `[tool.uv] package = true` + `[build-system]` hatchling + `[tool.hatch.build.targets.wheel] packages = ["app"]`，并**删掉 `readme = "../README.md"`**（指向 backend 外面，构建工具禁止越界）。结果 = **可编辑安装**（`.pth` 指向源码目录，改代码即时生效、无需重装），代价是 `uv run` / `uv sync` 每次多一次几秒构建检查（嫌慢用 `--no-sync` 或激活 venv 直接敲 `dev`）。

**验收**：`uv run worker` 起得来、连上远端 Redis、日志走项目统一格式；web 侧实测**不需 connect 即可 `enqueue`**（redis-py 懒连接），测试任务已清理；`uv run dev` 全生命周期（启动 → `queue.disconnect()` → 停止）无报错。**业务代码一行未碰**——`process_document` 仍跑 `BackgroundTasks`，迁移是下一刀。

### 2026-07-20 — Rerank 双域验收：eval 接精排 + 四组对照 + 实验发现录建档

**脚本改造**：`eval_recall.py` 调用入口从直连 retriever **上移到 `RetrievalService`**——rerank 的四步编排（粗排放大 → 精排 → 阈值 → 截断）住在调度层，绕过去就考不到真实管线（代价 = 每条 query 多一次 KB 主键查询，换「脚本与产品同源零漂移」这条铁律）；加 `--rerank-model`（收 UUID 或模型名）+ `rerank_ms` 入延迟账本 + 档案记 `rerank_model` / `rerank_window`；EXPLAIN 口径随精排自动改用放大后的窗口。**改造先自证**：电商 1000 题不带 rerank、参数与 `003300` 档案一字不差 → recall@10 0.929 / MRR 0.8192 **完全一致**，证明单级路径未被破坏，后续对照才站得住。

**四组结果（@3 口径——KB tool 只交 top3，精排的功劳只在窄口径显形）**：医疗 0.711/0.6613 → **0.7364/0.6836（+2.5pt/+2.2pt ✅）**；电商 0.882/0.8103 → 0.8541/0.7862（−2.8pt/−2.4pt ❌）。两个精排组各 6 条 `TimeoutError`（散落不成片 = 上游免费额度长尾，非限流非缺陷），最坏/最好情况估算后结论均不翻盘。耗时 5.0 → 2.7 条/秒，单次精排 p50 ≈440ms。

**结论**：**同一 reranker 一域立功一域帮倒忙 → 收益取决于域、不取决于模型**。机制 = 电商基线 MRR 0.81 意味着答案本就在第 1 名，精排把 30 条候选重新洗牌等于让 27 个干扰项与冠军再赛一次，**上升空间为零、下跌空间敞开**；医疗基线 0.66、答案常埋在第 2 名开外，有失地才谈得上收复。与 hybrid 双域结论合流升级成硬规律：**叠第二级打分器能否赚，取决于向量在该域有没有留下空间**（四域次一致）。**验证了产品设计**：KB 的 rerank 字段可空、选了才开、默认关——若做成默认开启，电商类库白亏 2.8pt + 一倍延迟。

**实验发现录建档**：新建 `backend/benchmarks/FINDINGS.md`（与 `results/` 同目录），格式「假设 → 做法 → 数字 → 结论 → 产品含义」，回填六轮（rerank 双域 / 电商加餐 / hybrid 权重 / 停用词+sparse 天花板 / BGE 前缀否决 / HNSW 两个凶手）。**动因**：结论此前只活在 context 最近迭代里，按维护规则迟早被压缩磨掉细节，而这些正是复盘/面试最值钱的部分。**三层分工钉死**：`docs/design/` 记打算怎么做、`benchmarks/` 记做了什么量出什么、`results/*.json` 存原始数字；并限定**只收自己跑出来的数字**，读别家源码的横评归 `notes/`（证据强度不同不能混）。

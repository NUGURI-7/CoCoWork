# RAG 检索实验发现录

> 每次基准实验的「假设 → 做法 → 数字 → 结论 → 产品含义」。
> 一次实验一节，倒序排列（最新在上）。

**与另外两样东西的分工**：

| 东西 | 装什么 |
|---|---|
| `results/*.json`（同目录） | 原始档案（机器写的数字 + 环境快照），只有数据没有解释 |
| `docs/design/knowledge-rag-benchmark-v1.md` | 基准**设施**的设计与路线（打算怎么搭这把尺子） |
| 本文档 | 用这把尺子量出了什么、据此改了什么决定 |

一句话分工：`docs/design/` 记**打算怎么做**，本目录记**做了什么、量出了什么**。

**证据类型限定**：本文只收「自己跑出来的数字」。读别家源码得出的结论（各框架 sparse 实现横评等）归 `notes/`——证据强度不同，混在一起会让人分不清哪条结论有数据撑腰。

`context.md` 只留一行指针，不复述本文内容——那边的「最近迭代」会被定期压缩，结论细节保不住，所以放这儿。

## 2026-08-01 · 标题链前置：这把尺子够不着的那一类改动

> ⚠️ **本节证据强度低于其余各节**：没有 recall / MRR，只有一份文档、8 个人挑的 query 的定性对照。
> 之所以仍然收进来，是因为最值钱的那条结论**是关于尺子本身的**——它决定了以后哪些改动别再往这条路上撞。

### 起因

子块拼标题（Contextual Retrieval 的轻量版：把段的标题链前置到子块再送 embedding）落地后想量收益，**发现量不了**。

### 尺子为什么够不着（本次最有价值的结论）

三层，一层比一层根本：

1. **`import_corpus.py` 绕过了产品管线** —— 它自己实现了切块 + embed（`_embed_group` / `_pack_groups`），不走 `document_processor`，送去 embed 的是裸 chunk。`prepend_title` 对它完全不生效。*（工程问题，改脚本可解）*
2. **`Paragraph.title` 在这套语料里被挪作他用** —— 第 169 行 `title=str(pid)` 存的是 Multi-CPR 的 passage id，第 228 行 `meta={"pid": int(p.title)}` 靠它对 qrels。就算改了脚本，拼进 embedding 的会是 `"12345"` 这种数字 ID。*（工程问题，但牵连 qrels 对齐）*
3. **Multi-CPR 是一行一个 passage 的 TSV，没有文档结构、没有标题层级** —— **不存在标题链可拼**。*（数据问题，改代码解决不了）*

**可复用的教训**：这把尺子是为**检索算法**造的——模式切换、融合权重、rerank、索引参数，它量过的东西**全都不依赖文档结构**。凡是依赖**文档层级 / 位置 / 上下文**的改动（标题链前置、late chunking、父子块窗口大小、引用溯源定位精度），这套语料一律够不着。要量必须换有结构的语料并重搭 qrels，成本是重搭半套设施。

### 退而求其次做了什么（定性，非评测）

两个只差 `prepend_title` 一个变量的库（同模型 `bge-m3`、同 chunk 参数），灌同一份带三级标题的真实文档（`docs/design/knowledge-rag-v1.md`，18 段 / 64 子块），8 个**故意不含原文措辞、只能靠层级归属才答得上**的 query 对跑 vector top5。

### 数字（样本极小，不构成结论）

- **首位命中**：8 个里 2 个不同。明确正例一个 —— 「处理管线分几个阶段」开组命中 `4. 文档处理管线`、关组命中 `13. 实施切片与顺序`；那段正文里**没有「阶段」二字**，只有标题层级说明了它是干什么的。
- **相似度分数**：8 个里 **5 个开组更低**，平均 **−0.027**，最大 **−0.100**。稀释是真实的、有量纲的。

分数下移本身不改变相对排序，但 `similarity_threshold` 是按绝对分卡的——阈值行为会跟着变。

### 一个没有验证条件的猜测

标题链含 H1（文档自己的标题）。实验库里只有一份文档，**18 个段的标题链全部共享这段前缀**，等于每条向量都掺进了同一段无区分度的文字——疑为分数普遍下降的主因。

对应改法是「拼的时候跳过最顶层」，但**方向取决于库里有几份文档**：多文档库里 H1 恰恰是区分「这段出自哪一份」的信息。这正是上面那条教训的实例——**判不了，因为尺子够不着**。

### 产品含义

- 功能保留，做成库级开关 `ChunkConfig.prepend_title`（该不该拼取决于文档的标题有没有信息量，本就该由建库的人定）
- **默认值暂不定** —— 没有数据支撑，只能在「业界默认拼」和「保守不改变现状」之间二选一，等有尺子了再说
- **状态如实记账：按业界共识做了（LlamaIndex `MetadataMode.EMBED` 默认拼、Azure 架构中心公开报 15-25pt），自己没有量化验证。** 这句话就是这条改动能说的全部，不要说过头。

## 2026-07-20 · Rerank 双域验收：二次打分的收益取决于域，不取决于模型

### 假设

Rerank 精排能收复 hybrid 欠下的 MRR 失地。原验收标准（片首定的）：「hybrid + rerank 的 recall@3 / MRR@3 同时压过纯向量」。

**开跑前标准就改了一次**：双域 @50 候选池对照已把 hybrid 判出局（电商域平局、医疗域仅 +0.2pt，两域都还要交 5pt 排位税），粗排定为纯向量。所以实际考题是 **「vector + rerank」能不能压过「vector 单级」**。

### 做法

- 口径改 **@3**：产品里 KB tool 只挑 3 条喂 LLM，第 4 名之后再准也见不着。精排的本事正是「把对的那条从第 8 名提到第 1 名」，这种功劳只在窄口径下看得见（@50 那种宽口径里等于白干）。
- 两域各跑一对（单级基线 / 两级），共四组，1000 题、`--workers 4`。
- 精排模型：硅基流动 `BAAI/bge-reranker-v2-m3`。粗排窗口 = `rerank_window(3)` = 30 条。
- 脚本改造：`eval_recall.py` 的调用入口从直连 retriever 上移到 `RetrievalService`——rerank 的四步编排（粗排放大 → 精排 → 阈值 → 截断）住在调度层，绕过去就考不到真实管线。

**改造先做回归自证**：电商 1000 题、不带 `--rerank-model`、参数与 `2026-07-20_003300` 一字不差 → recall@10 **0.929** / MRR **0.8192**，与旧档案完全一致（档案 `2026-07-20_190454`）。证明「不给 rerank 参数时走的还是原来那行代码」，后续对照才站得住。

### 数字

| 域 | 组 | recall@3 | MRR@3 | 档案 |
|---|---|---|---|---|
| 电商 | 纯向量 | 0.882 | 0.8103 | `191234` |
| 电商 | +精排 | 0.8541 | 0.7862 | `192812` |
| | | **−2.8pt** | **−2.4pt** | |
| 医疗 | 纯向量 | 0.711 | 0.6613 | `193451` |
| 医疗 | +精排 | **0.7364** | **0.6836** | `194653` |
| | | **+2.5pt** | **+2.2pt** | |

两个精排组各有 6 条 `TimeoutError`（30s 超时兜底触发），分母 994。失败散落不成片 → 是硅基流动免费额度的偶发长尾，非限流、非代码缺陷。**结论对这 6 条不敏感**：医疗按最坏情况（6 条全算失败）仍有 0.732 > 0.711；电商按最好情况（6 条全算命中）也才 0.855 < 0.882。涨跌都不是分母缩水缩出来的。

耗时：单级 5.0–5.2 条/秒 → 两级 2.6–2.7 条/秒，慢近一倍；单次精排 p50 ≈ 440ms（顺序跑采样，网络为主）。

### 结论

**同一个 reranker、同一套管线、同样的窗口，一个域立功、一个域帮倒忙。** 所以电商那 −2.8pt 不是模型不行，是域里没它的活干。

机制（电商为什么亏）：基线 MRR 0.8103 意味着**大部分题的正确答案本来就在第 1 名**。精排把粗排 30 条重新洗牌，等于让原本待在第 4–30 名的 27 个干扰项，重新和冠军同台竞争一次——**上升空间几乎为零，下跌空间敞开**。而电商语料恰恰最容易判错：商品标题又短又雷同（「红茶礼盒 250g」vs「红茶礼盒 500g」在 reranker 眼里近乎同一句）。向量反而稳，因为 query 和商品标题由**同一个 embedding 模型**编码，同一空间内比距离，属于同分布任务；reranker 是另一个模型、另一套标准，是外来户。

**原排名越准，请外人重批的收益越小、风险越大。** 医疗基线 MRR 才 0.6613、答案常埋在第 2 名开外，有真实的提拔空间，所以外来户标准即使不完美也能净赚。**有失地才谈得上收复。**

**与 hybrid 结论合并，升级成一条更硬的规律**：给向量叠第二级打分器——不管是关键词腿还是 reranker——能不能赚，取决于**向量在这个域上有没有留下空间**。向量吃干净的域，加什么都是噪音。目前有四个域次的数据支撑（hybrid×2 + rerank×2），四次全部一致。

### 产品含义

1. **精排按域选，不能无脑默认开。** 已落地的设计正好对应：KB 上的 rerank 模型字段可空、选了才开、默认关。要是当初做成默认开启，电商类库会被白坑 2.8pt 外加一倍延迟。
2. **成本要摆到台面上**：每次查询多约 0.5 秒。医疗域花这钱换 2.5pt 值；电商域花了还倒亏。
3. 前端配置面文案按此口径写：不承诺「开了更准」，而是「词面与语义差距大的库（专业术语、跨领域问法）值得开」。

### 遗留

- 医疗 +2.5pt 是在**纯向量粗排**上取得的。「hybrid 粗排 + rerank」这一组没跑——双域 @50 已判定 hybrid 连粗排岗位都竞聘失败，补跑只有考古价值。
- 精排窗口固定 `top_k×10`（=30）未做扫描。窗口更大是否能在医疗域再多捞几分，属顺手实验。
- 付费 reranker 对照（预算 100–200 元内）仍挂账。当前结论是「域决定收益」，换更强的模型大概率改变的是幅度而非方向。

## 2026-07-20 · 电商域加餐：hybrid 的域依赖假设，前半句证实、后半句反杀

### 假设

医疗域 hybrid 只赚 +0.5pt，怀疑是「域太偏语义、关键词腿太弱」。换到词面重合度高的电商域，关键词腿应该变强，hybrid 增益应该跟着变大。

### 做法

Multi-CPR 电商 split 灌库。**这里踩了个数据集陷阱，值得单独记**：医疗是官方切好的 4 个 split，1000 条 dev 答案恰好全在 split_1 的前 1 万行里；而电商/视频是单文件 corpus（各约 100 万段）、答案散布全量——直接取前 1 万行只命中 11/13 条，evaluator 会**空跑 989 题还不报错**，分数看着正常实则毫无意义。

解法：构造 `corpus_10k.tsv` = 1000 条答案段 + 前 9000 条非答案段，做成与医疗同构的 1 万段库，三域横比才成立。

**教训：评测数据集不能「顺手截前 N 行」，得先验证答案覆盖率。** 这个坑不报错、不崩溃，只是悄悄让整轮实验作废。

### 数字

| 电商 @10 | recall | MRR |
|---|---|---|
| vector | **0.929** | **0.8192** |
| keyword | 0.557 | 0.3329 |
| hybrid w=0.9 | 0.927 | 0.7632 |
| hybrid w=0.7 | 0.899 | 0.6781 |
| hybrid w=0.5 | 0.878 | 0.6193 |

候选池口径（@50，为 rerank 粗排岗位竞聘）：电商 vector 0.967 = hybrid 0.967 **平局**，MRR 照输 5pt；医疗 vector 0.910 vs hybrid 0.912（**+0.2pt = 仅 2 题独有救援**），MRR 税 5.2pt。

### 结论

**假设前半句证实**：同一套无 IDF 的 `ts_rank_cd`、同一张停用词表，换到词面重合域 recall ×2.7（0.205 → 0.557）、MRR ×4。医疗那场惨案，一半的锅是域的。

**后半句被反杀**：关键词腿强了近三倍，hybrid 增益反而从 +0.5pt 变成 ≈0，且权重扫描单调恶化——任何权重都打不过纯向量。

机制：**hybrid 的价值不在第二条腿有多强，而在它跟第一条腿有多互补。** 电商 query 与商品标题共享词汇表，向量已经把字面信息吃干净了，关键词提供不了正交信息，融合只是往排序里掺噪音。医疗两条腿是正交的（语义 vs 词面），所以 0.19 的弱腿反而有尾部救援价值。

**@50 深口径进一步打穿**：医疗那 +0.5pt 的救援在深口径反而缩水到 +0.2pt——因为向量自己挖到第 50 名时已收复 11pt 失地，keyword 救的大多是「向量排 11–50 名」的题，而非「向量彻底找不到」的题。2 题收益抵不过双腿查询成本。

**终局**：当前这条无 IDF 的 sparse 腿下，hybrid 全域无岗位（四轮考试闭环：@10 / 权重扫描 / 双域 @50）。rerank 片的粗排两域均用纯向量。翻案的唯一路径是换真 BM25 引擎后重考。

### 产品含义

hybrid 不能当无脑默认，检索 mode 应该按域选。向量强域直接 vector，词面弱域才值得考虑 hybrid——KB 的 mode 已经是可选项，文案和默认值按这个口径写。

## 2026-07-19 · Hybrid 融合：等权是陷阱，弱腿必须降权

### 假设

向量 + 关键词双路召回，用 RRF（倒数排名融合）合并，应该优于单路。

### 做法

`HybridRetriever` 双路 `asyncio.gather` 并发，复用两路现成 retriever 与 SQL——**刻意不写第三条 SQL**。（反例：MaxKB 的单 SQL blend 只有向量在真检索，关键词仅给池内结果加分，没有补召回能力。）融合用纯函数加权 RRF：关键词分数无 IDF 不可信，但**名次仍然有信息**——分数可信用分数、分数不可信退名次。

### 数字

| 医疗 @10 | recall | MRR |
|---|---|---|
| 纯向量基线 | 0.799 | **0.678** |
| hybrid 等权 | 0.758 ❌ | 0.474 ❌ |
| hybrid w=0.9 | **0.804** ✅ | 0.626 |

### 结论

**等权首跑直接倒退**，根因是「弱腿平等票权绑架共识」：一个垃圾段只要「关键词第 1 名 + 向量第 30 名」，融合分就能反超「向量第 1 名 + 关键词根本没召回」的正确答案。两条腿质量差三倍还给同等票权，等于让差生决定排名。

加权后 w=0.9 是峰值，recall 0.804 首次超过纯向量 0.799；w=0.95 是无用点。**注意 RAGFlow 的权重实证不可迁移**——它的权重乘在分数上，我们乘在名次票上，数字长在公式上，换个公式就失效。

**增益的真实规模要说清楚：+0.5pt = 1000 题里净救 5 题。** 而 MRR 反而从 0.678 掉到 0.626——这就是 RRF 的「排位税」：名次融合天然搅动榜首。这笔失地当时挂账给 rerank 去收复（后续证明：医疗域收复成功，电商域收不回来因为压根没失地）。

### 副产品：测试分工

融合公式写完后，两个真 bug（return 缩进、漏改归一化分母）**都是断言脚本抓出来的，肉眼 review 没看出来**。由此定下分工：**eval 考「策略好坏」，单测考「实现忠实」**——前者告诉你该不该用这个算法，后者告诉你代码有没有忠实实现它。两者不能互相替代。

## 2026-07-18 · 关键词检索：停用词的威力，与 sparse 的天花板

### 停用词三轮（最直观的一次调优）

同一个查询、同一套索引，只改停用词表：

| 轮次 | 前 5 条相关性 | 耗时 |
|---|---|---|
| 裸奔（无停用词） | **0/5** | 1301ms |
| Dify 停用词表（680 词） | 1/5 | 375ms |
| 补「好 / 很」两个词（682 词） | **5/5 满堂红** | **93ms（14 倍）** |

裸奔时「了 / 好 / 怎么」这类口水词霸榜——它们在几乎每一段里都出现，于是每一段都被判定为「匹配」。两个词的差距就是全军覆没和满堂红。

### sparse 基线定档与根因

| 医疗 @10 | recall | MRR |
|---|---|---|
| OR 全量分词 | 0.205 | 0.093 |
| `extract_tags` TF-IDF top10 | 0.19 | 0.083 |

第二种**不涨分但快 3 倍**，定为产品口径——hybrid 的 RRF 只吃名次，1.5pt 的分差换 3 倍速划算。

**根因结论（这条是核心认知）**：Postgres 的 `ts_rank` 家族**没有 IDF**，这是 sparse 质量的天花板。没有 IDF 意味着「的」和「幽门螺杆菌」在打分时同等重要。查询侧用 TF-IDF 提纯只能代偿「筛词」那半边，代偿不了「打分加权」那半边——**组合拳不能拆开抄**：OR 语义之所以在别家能用，前提是它们的打分器有 IDF。

### 三条可复用的原则

1. **全文索引要建在「返回单元」上**（五个项目横评一致验证）。
2. **引擎选型一票，顶配件层十票**——选 ES 白捡 Lucene 的 BM25，比在 PG 上精调分词器收益大得多。
3. **组合拳不能拆开抄**——照搬别家的某一招而不带上它的前提，通常是负收益。

### 副产品：评测脚本的健壮性

加了 `--workers` 并发、`--timeout` 单条超时、失败记名续跑、连败熔断。起因是远端 TCP 半死（连接断了不通知）导致**顺序跑到 460/1000 无声卡死**——脚本没崩、没报错，就是永远停在那里。生产系统里同一类问题会表现为「请求永不返回」，超时兜底是必需品不是可选项。

## 2026-07-17 · BGE query 指令 A/B：一个否决式结论

### 假设

BGE 官方建议 query 侧加检索指令前缀（"为这个句子生成表示以用于检索相关文章："），加上应该涨分。

### 数字

1000 题实测：**+0.2pt recall / +1pt MRR**。

### 结论

**决定不进产品。** 收益太小，而代价是要按模型维护一张指令表——换 embedding 模型就得同步改，属于长期负债。Dify / RAGFlow 的取舍也一样。

代码里保留了实测记录（`vector.py` 的 known-gap 注释改成「已实测、主动关闭」），`--query-prefix` 参数留在评测脚本里备查。

**这轮的价值不在数字，在于它是基准第一次走完「假设 → 实验 → 数据 → 决策」的完整闭环，而且得出的是否决式结论。** 官方推荐 ≠ 你的场景该用，得自己量。

## 2026-07-16 · HNSW 实战：索引建好了却不被用的两个凶手

### 数字

| 医疗 1 万段 @10 | 无索引 | 建 HNSW 后 |
|---|---|---|
| 服务端 p50 | 237ms | **11.8ms（20 倍）** |
| recall@10 | 0.799 | 0.799 |
| MRR@10 | 0.678 | 0.678 |

**提速 20 倍、召回一字不差**——ANN 的近似损失在这个规模和参数下为零。

### 两个凶手（索引建完了，查询就是不走它）

**凶手一：SQL 形状不对。** 旧 SQL 内层用 `DISTINCT ON` 按段 id 排序，等于扫全量再去重。HNSW 只认「`ORDER BY` 距离 + `LIMIT N`」这一种形状，其他写法一律退化成顺扫。重构成 CTE 三段：候选池（top_k × 5）→ 按段去重 → JOIN + 阈值 + 截断。

顺带一个暗坑：`hnsw.ef_search` **默认值 40**，候选池要 200 也照样只给你 40，静默截胡、不报错。事务里 `SET LOCAL` 显式抬高才行。

**凶手二：规划器成本误估。** 1024 维的距离运算被 PG 估得太便宜，小表上它算出「顺扫更划算」——估价 1480 vs 2553，实测却是 176ms vs 3ms，**完全倒挂**。解法是 `SET LOCAL enable_seqscan = off`（pgvector 官方姿势），没建索引的库仍会顺扫兜底，不会炸。

### 一条测量口径的决策

建索引后**客户端**测得的耗时几乎没变，服务端却快了 20 倍。原因：一次检索有 5 次网络往返（笔记本 → 远端 PG），RTT 把省下的 225ms 完全淹没了。生产环境同机部署没有这一项。

由此定下：**基准测量砍掉网络只看服务端执行时间（EXPLAIN ANALYZE 采样），生产监控则看全程。** 两个场景问的是不同的问题——基准问「我的算法改进有没有效」，监控问「用户等了多久」。

### 一个数据毒药踩坑

bge-large-zh-v1.5 输入上限 512 token，超长 passage 直接被上游返 400，重试无用。第一反应是截断，但被否——**评测口径必须与产品一致**。改成「embed 阶段复用产品的 splitter 切块」，与正式管线同款（一段切 N 块，检索侧 `DISTINCT ON` 天然支持）。

如果当时图省事截断了，测出来的就不是产品的真实表现。
